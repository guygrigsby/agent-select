VERDICT: FAIL

## Blockers

1. **Crash between `publish_snapshot` and `retire_snapshot` permanently orphans the predecessor's retirement; the redelivery resolves as a freshness confirmation instead of completing the pipeline.**
   `internal/collector/successor.go:243-268` (`AttemptSuccessor`) derives everything from `latestPublication` at attempt time. Sequence: attempt publishes P2 and crashes before `RetireSnapshot` commits; no receipts were recorded, so the batch redelivers; the redelivery now sees P2 as `prev`, recompiles at a new attempt instant, finds masked-unchanged content (`contentEqual`) and returns `SuccessorConfirmed` — `P1` is never retired. Nothing else ever retires it: the next changed generation retires P2, not P1. `snapshot_retirements` and the `SnapshotRetired` event are silently lost forever, contradicting the at-least-once contract ("records no receipts, so the batch redelivers" implies the redelivery completes the work) and the normative step "retires the predecessor via `retire_snapshot` naming the successor hash and the new publication ID".
   Live-probed (`TestProbeP13RetirementLostOnRedelivery`, since removed): after a manual publish-without-retire, the redelivery returned `confirmed` and `snapshot_retirements` held 0 rows for gen1's hash. Fix shape: on the unchanged/confirmed path (and at reconciliation), retire any older publication on the channel that has no retirement row, naming the latest publication — or carry a durable per-batch pipeline mark so a redelivery resumes rather than re-derives.

2. **Double-hash class: event payload digest fields and the artifact locator carry `hex(sha256(artifact_hash))`, not `hex(artifact_hash)` — and Phase 13's store names files with the true hex, so `artifact_locator` resolves to no store path.**
   `hexHash(b)` is `hex(sha256(b))` (`internal/collector/canonical.go:84`). Applying it to an already-computed 32-byte digest re-hashes it. New code in this commit:
   - `internal/collector/successor.go:83-85` — `RetireSnapshot` payload `"artifact_hash": hexHash(artifactHash)` and `"successor_hash": hexHash(successorHash)`: both carry hash-of-hash, matching no row in `snapshots`/`snapshot_publications`.
   - `internal/collector/successor.go:73` — the error message prints `hexHash(successorHash)` as the successor hash: wrong value shown to callers.
   Meanwhile `ReconcileStore`/`store.go` name files `hexDigest(pub.ArtifactHash)` (correct, spec: `<root>/snapshots/<hex(artifact_hash)>.bin`), so the DB's `artifact_locator` (`snapshot://<hexHash>` — pre-existing `artifactLocator` in `snapshot.go:332`, same defect in `SnapshotCompiled`/`SnapshotValidated`/`SnapshotPublished` payloads) points at a hash that matches no file. Any consumer resolving the locator to the Phase 13 store gets a miss.
   Live-probed: all 5 `artifact_hash` payload fields across the three snapshot event names matched **no** real snapshot hash; the payload dump shows `artifact_hash` identical to the `snapshot://` locator suffix while store files sit at the true hex. This is systemic (the emitter-side instances predate this commit and passed earlier rounds), but this commit both extends it (`RetireSnapshot`) and builds the first locator-consuming layer on the correct convention, making the divergence functional. Fix sweep: use `hexDigest` for every already-computed digest (payload fields, locator, error message), including the pre-existing emitters, and pin it with a test that decodes `SnapshotPublished`'s payload against `snapshot_publications.artifact_hash`.

## Non-blocking notes

- **Spec sentence "No snapshot row, no publication" is not honored on the unchanged path.** Every attempt compiles at a new attempt instant, so each unchanged batch inserts a full `snapshots` row (artifact bytes included). Probed: `snapshots` rows 1 → 2 across one unchanged attempt. Either implement (pre-check is impossible without compiling, so this means a spec amendment or masking-before-persist) or amend the sentence to "no new publication"; the append-only table grows one full row per trigger batch either way.
- **"the rejection findings are logged" is unimplemented.** `successor.go:284-286` returns `SuccessorBlocked` and discards `validation.Findings`; the package has no logging at all.
- **Semantic-block and debounce paths are untested.** No test drives validation-rejected → receipts recorded with the prior generation intact, nor publish `forbidden`/`conflict`/`source_blocked` → blocked; nothing asserts one batch of N triggers yields exactly one attempt (the debounce is real in `RunSuccessorLoop` — `attempt` flag, one `AttemptSuccessor` per batch — but unproven).
- **No concurrent-publisher guard.** Two processes running the `publisher` consumer both scan the same undelivered batch (no claim/lease in `DeliveryScan`), compile distinct snapshots (different attempt instants) and both publish — messy but converging (newest-published wins). Spec says one loop per channel; safe only under that deployment assumption.
- **A malformed `CURRENT` file bricks the loop instead of healing.** `store.go:139-141` returns a storage error; startup reconciliation then fails and `RunCollectorWith` exits. The spec pitches the store as derived and rebuildable; reading `CURRENT` could fall back to re-adoption instead.
- **Persistent config-error hot-retry, silently.** `AttemptSuccessor` maps "no projection policy: bootstrap configuration is required" (`CodeInvalidRequest`, permanent) to the same no-receipts + 5s-retry path as transient storage errors, with no log; a misconfigured daemon retries forever with no signal.
- **In-process store staleness window.** If publish succeeds and `ReconcileStore` fails transiently, the in-process redelivery confirms freshness without reconciling; the store stays one generation behind until the next changed publication or restart (startup reconciliation heals it). The retirement blocker's fix should cover this too.
- **`RetireSnapshot` idempotent replay does not compare the stored `successor_hash`** — a replay with the same `(artifact_hash, publication_id)` but a different successor returns nil (`successor.go:57-63`). Unreachable from the pipeline; tighten while fixing blocker 2.
- **Dead code and a misleading follow-up commit.** `Ports.materialize` (`successor.go:356-360`) is uncalled; `4c2ac7e` is titled "drop dead materialize wrapper from successor pipeline" but only touches `.beads/issues.jsonl` — the wrapper is still there.
- **Spec-internal tension:** the V8 lead sentence says the loop runs "when the configuration carries a channel" while the field list makes `snapshot_validator_version` required; the implementation gates on the validator version (`daemon.go:103`). Field list is the sensible reading; consider fixing the lead sentence.
- Config defaults (`daemon.go:104-129`) match the spec names/defaults exactly (`snapshot_channel` local, `snapshot_distribution` local, `store_keep_generations` 2, `<UserConfigDir>/agent-routing/store`); no unit test covers `SuccessorConfigFrom`, but the mapping is trivial. Explicit `store_keep_generations = 1` fails at store construction (floor 2) — fail-fast, fine.

## Blockers

1. **`SnapshotRetired` payload member contradicts the normative V8 payload grammar: code emits `artifact_hash`, spec says `retired_hash` — every spec-conformant consumer fails to decode the event.**
   `internal/collector/successor.go:131-136` emits the closed payload `{artifact_hash, successor_hash, publication_id}`. `docs/specs/delivery-storage.md` (Event payloads) pins `SnapshotRetired` as "`retired_hash`, `successor_hash`, `publication_id`. Self-contained." Payload schemas are closed: a consumer strict-decoding per the spec rejects every real event (unknown member `artifact_hash`, missing `retired_hash`). Live-probed: decoded payload bytes `{"artifact_hash":"462d…","publication_id":"pub-f853…","successor_hash":"fbb5…"}`. Note the committed test `TestSuccessorEventPayloadsCarryTrueHex` pins the code's member name, so the suite currently enforces the drift. The DDL-side `snapshot_hash`→`artifact_hash` reconciliation note in the spec covers table columns only, not this payload member. Fix is one word on one side, contract-first (spec amendment or code rename, then update the test key).

2. **Round 1 blocker 2's hash-of-hash class persists in three payload fields: `input_manifest_hash` and `coverage_digest` carry `hex(sha256(digest))`, matching no row.**
   `internal/collector/snapshot.go:316-317` (`SnapshotCompiled`: `"input_manifest_hash": hexHash(manifestHash)`, `"coverage_digest": hexHash(coverageDigest)`) and `snapshot.go:1164` (`SnapshotPublished`: `"coverage_digest": hexHash(coverage)`), where `manifestHash`/`coverageDigest` are the already-computed digests stored in `snapshots.input_manifest_hash` / `snapshots.coverage_digest`. `hexHash` re-hashes (`canonical.go:85`), so the payload values equal `sha256(column)` and differ from the column. Live-probed: `payload manifest=5dd4efb1… != column f86a639f…; sha256(column)=5dd4efb1…` and likewise for coverage. The events claim to be self-contained facts and cross-referencing them to their rows fails, the exact failure mode round 1 blocker 2 described for `artifact_hash`. Round 1's fix instruction was "use `hexDigest` for every already-computed digest (payload fields, locator, error message), including the pre-existing emitters"; the sweep covered `artifact_hash` fields, locators and error text only (all verified fixed), leaving these three. (`findings_hash` at `snapshot.go:1020` is correct: it hashes raw canonical findings bytes, not a digest. Nothing consumes these three fields today, but the fix claim's own sweep is incomplete.)

3. **The convergence sentence amended into V8 in this very commit is half-implemented: blocked resolutions and every reconciliation skip the sweep.**
   Spec: "Retirement converges: every resolved attempt and every reconciliation retires any older publication on the channel that lacks a retirement row, naming the current publication." Code: `sweepRetirements` runs only on the confirmed path (`successor.go:55-63` via `resolveUnchanged`) and the published path (`successor.go:438`). The blocked resolutions at `successor.go:416-419` (validation rejected) and `successor.go:421-427` (publish `forbidden`/`conflict`/`source_blocked`) return `SuccessorBlocked` without sweeping, and `ReconcileStore` (`successor.go:446-476`) — the startup reconciliation at `successor.go:516` and the post-adoption reconciliation — contains no sweep. A blocked resolution is a resolved attempt (receipts are written, the batch is consumed), so a crash-window orphan that coincides with a persistently blocked successor stalls indefinitely with no redelivery and no restart-time heal. Mitigating: the round-1 orphan scenario itself converges (redelivery always re-resolves confirmed/published and sweeps), and the blocked paths are near-unreachable externally (probed: revocation produces a clean empty-projection publish, not `forbidden`; validation rejects only on internal-consistency corruption; `conflict` on same-hash republication is shadowed by the unchanged-hash check). The fix is small: sweep before each blocked return, and sweep at the end of `ReconcileStore` or after startup reconciliation — or amend the sentence to match the code.

## Non-blocking notes

- **Any-row retirement basis is channel-blind.** `sweepRetirements`' `NOT EXISTS (… WHERE r.artifact_hash = p.artifact_hash)` (`successor.go:152-154`) ignores which publication the retirement names, while the PK is `(artifact_hash, publication_id)`. One channel's retirement suppresses another channel's sweep forever if the same artifact hash is published to two channels. Unreachable in this slice (local-only distribution, `publish_snapshot` refuses local artifacts on distributable channels); will bite the distributable slice. Suggested shape: correlate the retirement's `publication_id` to this channel's publications.
- **`RetireSnapshot`'s new replay-conflict branch is untested.** `successor.go:87-96` compares stored `successor_hash` and returns `conflict` on mismatch (verified by reading), but no test drives a same-`(hash, publication)` replay with a different successor.
- **Corrupt `artifact_bytes` on the current publication is fatal with a misclassification.** `contentEqual` maps decode failure to `invalid_request` (`successor.go:373-380`), which `processOneBatch` treats as permanent misconfiguration and stops the loop (`successor.go:556-559`). Loud stop on corrupt evidence is defensible; the error code and the "misconfiguration" framing are off, and no backoff/heal path exists.
- **Scan and receipt storage errors are still fatal.** Only attempt errors back off; `DeliveryScan`/`RecordConsumerReceipt` failures propagate out of `RunSuccessorLoop` (`successor.go:521-531`) and exit the daemon. Spec mandates backoff only for the attempt case, and a supervisor restart heals; durability nit.
- **Commit message inaccuracy:** "unchanged-content path reconciles the store and sweeps retirements before confirming freshness" — code confirms freshness first (`resolveUnchanged`, `successor.go:55-63`). The spec requires only "before stopping", which the code satisfies.
- **`CollectorConfig.SnapshotPollIdle` has no TOML tag** (`daemon.go:32`), so no config key binds it; the spec names no such key and the 5s default always applies. Test-only field today.
- **Policy-version convention remains `hexHash(config_hash)`** (`successor.go:294`, `snapshot.go:139`) while two spec sentences say inputs pin "the hex `config_hash`". Self-consistent between `eligibleInputs` and the compile rights gate (round 1 verified the agreement), pre-existing, and load-bearing; worth a spec amendment or ADR eventually, out of scope here.
- Carried from round 1, unchanged: no concurrent-publisher claim/lease on `DeliveryScan` (safe under the spec's one-loop-per-channel deployment; the sweep converges newest-published-wins even when two publishers interleave, though a publish between `PublishSnapshot` and the sweep can shift which publication the retirement names). `_ = pubRes` at `successor.go:428` discards the publication ID the sweep then re-derives.

## Verified claims

- **Round 1 blocker 1 fix (orphaned retirement): verified, with one residue (blocker 3).** `TestSuccessorRetirementConvergesAfterCrash` genuinely simulates the window: bootstrap publish, then compile+validate+publish of a changed successor with no reconcile/retire, then a redelivery attempt that re-derives from the new current publication, finds masked-unchanged content, and must both confirm freshness and converge. Assertions cover the retirement row `(P1 → P2 hash)`, its pairing to the publication whose `artifact_hash` is P2, and the store pointer landing on P2 (the crash also skipped materialization; `resolveUnchanged`'s `ReconcileStore` heals that too). Against `edf020f` this test fails (no retirement rows), so it discriminates.
- **Sweep mechanics.** `sweepRetirements` handles multiple orphans: it selects every channel publication whose hash differs from the current one and lacks any retirement row, ordered `published_at, id` ascending (oldest first), and retires each naming the current publication. The current publication cannot retire itself (hash inequality; same-hash re-publication on a channel is impossible by `UNIQUE (artifact_hash, channel)`). No-publication channels return early. Re-running is idempotent via the retirement PK. Crash windows inside `resolveUnchanged` (after `ConfirmFreshness`, after `ReconcileStore`, mid-sweep) all converge on redelivery: each step is idempotent or PK-deduped, receipts land only after the whole resolution.
- **Unchanged path idempotence across repeated redeliveries:** each redelivery appends one freshness row at a new instant (PK `(hash, channel, confirmed_at)`, `ON CONFLICT DO NOTHING` — matches "idempotent per (hash, channel, instant)"), publications stay fixed, pointer unmoved, store reconcile converges (`TestAttemptSuccessorUnchangedConfirmsFreshness`).
