# Source-access contract review — docs/specs/source-access.md

Pinned md5 `e49ef368c8295ca9218843792d5e953a` verified at review start and re-verified mid-review; no drift.

## Findings

**1. [BLOCKER] `not_found` is not in either closed error taxonomy.**
source-access.md:27: "Errors are the operator-port convention: `not_found` (unknown source), `conflict` (lifecycle violation), `invalid_evidence` (evidence rule above), `invalid_request` (malformed fields)."
contracts.md:20: "Closed error taxonomy: `invalid_request`, `unauthorized`, `forbidden`, `stale_lease`, `conflict`, `source_blocked`, `invalid_evidence`, `identity_unresolved`, `snapshot_unavailable`, `schema_incompatible`, `stale_required_fact`, `no_admissible_offer`, `budget_exceeded` and `temporarily_unavailable`."
delivery-storage.md:20: "the closed error code list for storage ports is `invalid_request`, `unauthorized`, `forbidden`, `stale_lease`, `conflict`, `source_blocked`, `invalid_evidence`, `identity_unresolved`, `temporarily_unavailable`."
No closed list contains `not_found`; the routing-only codes (`invalid_snapshot` etc.) are explicitly owned by educated routing and raised by no storage port. All four new ports can hit "unknown source", so the spec mandates an error token its owning specs forbid. (The `not_found` hits in research-artifact.md are research access-state tokens, a different vocabulary.)

**2. [BLOCKER] The terms-evidence retention path is unsatisfiable as specified — circular dependency.**
source-access.md:23: "no permission is `allowed` unless terms evidence exists (a retained terms observation or a retained failed observation documenting inaccessibility plus an operator attestation recorded in `license_text`)."
source-access.md:45: "Every policy with an `allowed` permission is backed by retained evidence: a terms observation capturing the terms or license bytes at a resource URL…"
The only ports that create observations are `record_attempt` (collector worker, fetch stage — delivery-storage.md) and `record_receipt` (host). A fetch job is authorized, per this spec, "only while `research` is `allowed` at execution time" (source-access.md:49), and `enqueue_job` requires the source to "allow this use" (contracts.md). With no policy registered the governing set is empty and every production use is denied (source-access.md:35), so the collector can never fetch the terms page that would allow the first registration. The fetch scope is also "only against the host of a registered source URL" (source-access.md:49) while `terms_url` is a separate field that may live on a different host, so even a post-allowance production fetch of the terms URL is out of scope. No operator evidence port exists in contracts.md or delivery-storage.md, and the spec claims it invents none. Result: no conforming first registration can ever be produced. The slice definition ("retained evidence and audit requirements") is not closed.

**3. [MAJOR] The same-time-conflict "until" clause contradicts the governing-set definition when the conflicting rows have different `expires_at`.**
source-access.md:35: "Two or more rows sharing that greatest `effective_at` with different `config_hash` values are a same-time conflict: no row governs, every production use of the source is denied at `T` until a strictly later-effective policy is registered."
Set semantics from the same line: at T past the shorter twin's expiry the set is no longer tied, the surviving row governs, and uses are admitted — without any registration. Example: A (effective 10:00, expires 12:00) and B (effective 10:00, expires 14:00): denied at 11:00, but at 13:00 the set is {B} and B governs. Two implementable readings diverge on admit vs deny. The verification list (source-access.md:57) pins only "clearing after a later-effective registration", never the expiry-clear case.

**4. [MAJOR] Disable-as-revocation contradicts "lifecycle flags only" and both owning gates.**
source-access.md:41: "Revocation is a later-effective registration setting the affected permission to `denied` (or `unknown`), or source disable. Effects are exactly the delivery-storage gates: successor compiles exclude the source's inputs…"
source-access.md:25: "disable_source(source_id) / enable_source(source_id): lifecycle flags only. … Disabling never rewrites policy history and never revokes already-published artifacts."
delivery-storage.md:46 compile gate: "Compilation requires, for every contributing source, the current newest effective non-expired policy with `research` and `extraction` allowed" — `sources.enabled` is not read. delivery-storage.md:48 publication gate re-evaluates "current policies", likewise not `enabled`. So for a disabled source with a still-valid allowed policy, successor compiles do NOT exclude its (previously retained) inputs and the publication gate passes — the blanket revocation sentence is false for the disable form. An operator disabling a source for rights reasons leaves its material flowing into snapshots.

**5. [MAJOR] The operator port surface collides with the owning spec's method list.**
source-access.md:24: "`register_source(id, url, source_kind, parser_version, freshness_ceiling_seconds)`"
contracts.md:24: "`register_source(Source)` and `revise_source(Source)`: Operator; … Request is all Source fields from the domain model." — Source fields include `access_policy` and `enabled` (domain-model.md:37), so the two same-named ports have different request shapes. contracts.md routes disabling through "revised enabled state"; domain-model.md:39: "disabled to enabled through `RevisePolicy` with an allowed policy. No other transitions." — while source-access.md:25 adds standalone `enable_source`/`disable_source` ports. The spec declares "Where wording conflicts, the owning spec governs" (source-access.md:3), which makes its own new port names unowned surface: neither `register_source_policy` nor `disable_source`/`enable_source` exists in contracts.md or delivery-storage.md, and the spec names no aggregate method (`Source.RevisePolicy`, `Source.Disable`) for them.

**6. [MAJOR] Stage-to-permission gate mapping and instants are unpinned for parse and resolve.**
source-access.md:37: "Evaluation instants: fetch authorization is evaluated at job enqueue and again at lease acquisition…; snapshot compilation evaluates inside the compile transaction; publication re-evaluates inside the publication transaction…"
Only fetch, compile and publication are pinned. `extraction` "authorizes deriving typed assertions from retained material for production use" (source-access.md:13) — the parse stage derives assertions, yet no instant is defined at which extraction permission is evaluated for parse jobs (enqueue? lease? record_attempt?), and the resolve stage has no permission mapping at all. contracts.md `enqueue_job` requires the source to "allow this use" (contracts.md) without defining "use" per stage. A parse job for a source whose extraction flipped to `denied` mid-pipeline has no specified behavior.

**7. [MINOR] Evidence is not bound to `terms_url`, and no outcome tokens pin the failed-observation path.**
source-access.md:45: "a terms observation capturing the terms or license bytes at a resource URL" — any resource URL. Nothing requires the qualifying observation's `resource_url` to equal the policy's `terms_url`, so the structural evidence check (source-access.md:23) can be satisfied by an observation of unrelated material; the principle sentence ("data rights must be established from the terms that govern the fetched material", source-access.md:9) has no enforcement point. Likewise "a retained failed observation documenting inaccessibility" never says which `observations.outcome`/status combinations qualify (`http_error` ≥400? `source_blocked` 401/403/429/451 per delivery-storage.md?).

**8. [MINOR] Policy resurrection after an expiring revocation is unstated.**
Set semantics (source-access.md:35) mean a time-boxed `denied` registration silently re-admits the prior `allowed` policy when the denial expires — P1 allowed (Jan 1–Mar 1), P2 denied (Feb 1–Feb 15): allowed again on Feb 15 with no operator action and no fresh terms re-check, against the spec's own principle "the system never silently extends a policy" (source-access.md:45). Deterministic and operator-authored, so not major, but the semantics should be named and the case added to verification.

**9. [MINOR] Success responses and replay semantics for the new ports are unstated.**
`register_source_policy` specifies idempotent replay ("identical replay returns the stored row", source-access.md:23) but never states the success response of a fresh registration (contracts.md gives `register_source` "Response is source ID and configuration hash"). `disable_source`/`enable_source` responses are unstated, and replaying an identical disable (or disable of an already-disabled source) is only implicitly `conflict` via "`conflict` (lifecycle violation)" (source-access.md:27).

**10. [MINOR] Dangling reference "the rights contract's rollback rules".**
source-access.md:41. No spec is named "rights contract". Rollback rules live in collection-pipeline.md:71 ("Retain at least two verified versions and support rollback") and contracts.md (`SnapshotRetention` owns "rollback eligibility"). Name the owning document.

**11. [NOTE] `SourceAdmission` cannot decide "when a governing policy appears" from the `SourcePolicyChanged` payload.**
The payload (delivery-storage.md:59) carries `source_id`, `config_hash`, `enabled`, permissions, `parser_version` — no `effective_at`/`expires_at` and no conflict information. Determining whether a governing policy exists requires re-evaluating precedence over `source_policies` rows at consumption time (an event alone cannot know about future-effective siblings or conflicts). Consistent, but worth one sentence so the consumer contract is explicit.
